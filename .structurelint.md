# structurelint Setup

This project uses [structurelint](https://github.com/Jonathangadeaharder/structurelint) to enforce project structure, organization, and architectural integrity.

## What is structurelint?

structurelint is a next-generation linter that focuses on enforcing project structure rather than code quality. It validates:

- Directory depth and file organization
- Naming conventions (PascalCase, camelCase, etc.)
- File count limits per directory
- Required file existence
- Disallowed patterns
- Architectural layer enforcement

## Installation

structurelint is built with Go and needs to be installed separately:

```bash
# Clone and build from source
git clone https://github.com/Jonathangadeaharder/structurelint.git
cd structurelint
go build -o structurelint ./cmd/structurelint

# Copy binary to PATH
sudo cp structurelint /usr/local/bin/
```

Or download pre-built binaries from the releases page.

## Usage

Run structurelint checks:

```bash
# Using npm scripts (recommended)
npm run lint:structure

# Watch mode for continuous checking
npm run lint:structure:watch

# Direct command
structurelint .
```

## Configuration

The project's structurelint rules are defined in `.structurelint.yml`. Key rules include:

### Directory Structure Rules
- **Max depth**: 4 levels of nesting
- **Max files per directory**: 25 (default)
- **Max subdirectories**: 15

### Naming Conventions
Structurelint validates filenames (without extensions) to ensure consistency:

- **Components** (`src/components/**/*.js`): PascalCase (e.g., `LoadingSpinner.js`)
- **Screens** (`src/screens/**/*.js`): PascalCase (e.g., `HomeScreen.js`)
- **Hooks** (`src/hooks/**/*.js`): camelCase (e.g., `useAsyncData.js`)
- **Utils** (`src/utils/**/*.js`): camelCase (e.g., `validation.js`)
- **Services** (`src/services/**/*.js`): camelCase (e.g., `apiClient.js`)
- **Context** (`src/context/**/*.js`): PascalCase (e.g., `AuthContext.js`)
- **Core** (`src/core/**/*.js`): camelCase (e.g., `gamification.js`)
- **Data** (`src/data/**/*.js`): camelCase (e.g., `pokerRanges.js`)
- **Tests** (`__tests__/**/*.js`): camelCase (e.g., `gamification.test.js`)
- **Documentation** (`docs/**/*.md`): SCREAMING_SNAKE_CASE (e.g., `USER_GUIDE.md`)

Additional regex validations:
- **Hooks**: Must start with `use` followed by uppercase letter
- **Context files**: Must end with `Context`
- **Test files**: Must end with `.test.js`

### Disallowed Patterns
- `**/*.tmp` - Temporary files
- `**/*.backup` - Backup files
- `**/TODO.txt` - Use issue tracking instead
- `**/.DS_Store` - macOS system files

## CI/CD Integration

You can add structurelint to your CI/CD pipeline:

```yaml
# Example GitHub Actions workflow
- name: Run structure linting
  run: |
    npm run lint:structure
```

## Modifying Rules

To modify the rules, edit `.structurelint.yml`. After making changes:

1. Run `structurelint .` to validate
2. Fix any violations or adjust rules as needed
3. Commit the updated configuration

## Benefits

- **Consistency**: Enforces uniform project structure across the team
- **Maintainability**: Prevents directory bloat and deep nesting
- **Onboarding**: New developers can understand project organization quickly
- **Quality**: Catches organizational issues before they become problems

## Advanced Features

This installation includes structurelint's core filesystem linting features. The tool also supports advanced capabilities that can be configured as needed:

### Available Phases
- **Phase 0** (Configured): Filesystem linting with naming conventions and structural limits
- **Phase 1**: Architectural layer enforcement and import graph analysis
- **Phase 2**: Dead code detection (orphaned files and unused exports)
- **Phase 3**: Test validation and adjacency enforcement
- **Phase 4**: File content templates for documentation
- **Phase 5**: Evidence-based metrics (Cognitive Complexity, Halstead metrics)
- **Phase 8**: GitHub workflow enforcement

### Language Support
While this project uses JavaScript, structurelint supports multi-language validation:
- JavaScript/TypeScript, Go, Python, Java, C++, C#, Rust, Ruby

### Future Enhancements
You can extend the current configuration by:
1. Adding layer boundary enforcement for architectural patterns
2. Enabling dead code detection
3. Requiring tests for all source files
4. Validating documentation structure with content templates

See the [structurelint documentation](https://github.com/Jonathangadeaharder/structurelint) for configuration examples.
